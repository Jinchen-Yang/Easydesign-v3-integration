## UI-027：资源探针加载态与满载超时校准

- 状态：`smoke-validated`。
- 完成时间：2026-08-02T16:28:55+08:00

### 完成内容

- 真实 18769 曾同时服务新静态资产和重启前导入的旧 Python 表单契约，造成位置选择已更新、
  但 Stage 04 三张事实卡与旧启动文案仍存在；完成无损服务切换后统一到当前源代码。
- 逐卡弹窗新增独立 `loading` 状态。请求未完成时明确显示“正在读取逐卡状态”，结果返回
  后原地更新；只有请求终态失败且没有快照时才显示“逐卡探针暂时不可用”。
- Suzhou2 schema 0.3 probe 会同时运行三后端活性检查；8 GPU 满载实测 35.58 秒，因此
  控制端上界由 8 秒校准为 60 秒。目标卡仍立即可选，不因等待自动回退本机。

### 验证证据

- Workbench Chromium 定向回归通过：挂起 `/execution-targets` 时弹窗显示加载态且不含
  “暂时不可用”，释放请求后同一弹窗显示 8 张 GPU。
- Python execution-target 定向测试 2/2 通过；类型构建通过。
- 真实 Suzhou2 返回 8 张 A100 快照、0/8 可立即使用和 1 条运行中任务；GPU 0–5 为外部
  compute process，GPU 6–7 同时有 EasyDesign lease。真实 18769 弹窗在约 36 秒后从
  加载态原地更新为 8 张卡。

### 遇到的问题

- 运行中的 Python 服务保留了重启前导入的表单契约；同时，逐卡弹窗无法区分请求尚未
  返回和请求已经失败。满载 Suzhou2 的完整受管 probe 又超过原 8 秒上界。

### 解决办法

- 无损重启只负责 localhost UI/API 的进程；前端显式建模 loading/error，控制端按真实
  35.58 秒观测将有限上界校准为 60 秒，目标选择仍与资源结果解耦。

### 遗留问题

- Manager 的资源快照仍与三后端活性检查共用一次 probe，满载时约需 36 秒；后续可在
  保持固定 allow-list 和租约事实的前提下拆分轻量资源投影，但本轮不重启活跃 worker。

### 安全边界

- 只重启无子进程的 localhost UI/API 服务；Suzhou2 systemd Manager 和既有 Stage 04
  worker 未重启、未终止，历史 run、环境、模型和队列记录未删除、移动或覆盖。
