- `make check`、`make test`、`make build`、PyMOL import 和真实 PSE 集成测试通过。

### 遇到的问题

- PyMOL headless 初始化后，短命 Python 进程必须显式 flush/quit 才能可靠返回版本文本。

- 版本探针显式写 stdout、flush 并退出 PyMOL，且必须精确匹配 `3.1.0`。
- worker 用 `cmd.iterate` 取得逐 CA color index，再解析 RGB/hex 并校验颜色计数。
- core 从已验证的标准残基顺序补全 entity sequence，再生成连续 `label_seq_id` 的 mmCIF。
- adapter 同时检查进程码和 response `status/error_code`，成功退出但失败 response 仍按失败
  处理；没有 fallback。

- PSE 当前被视为可信本地输入；UI 公开上传前需要独立安全沙箱和资源限制。
- 复合物、receptor/ligand、多聚体、非标准残基、配体保留和人工选择必须通过新契约实现，

- PSE 颜色只是一项用户来源 annotation；Stage 02 必须独立记录将其转成 hotspot 证据的

### 验证证据

- 143-aa 输入和临时 FASTA 均有效；旧日志显示提交成功后一直 `PENDING`，没有输入解析错误。
- 新对照中 Protenix 官方 endpoint 的 ticket 在 120 秒内持续 `PENDING`；实际 ColabFold

  runtime-only 证据位于
  `runs/_validation/protenix-apoe-msa-backed-smoke-20260724-001`。

### 遇到的问题

- Protenix 2.0.0 默认
  `MMSEQS_SERVICE_HOST_URL=https://protenix-server.com/api/msa`；
  `--msa_server_mode colabfold` 只改变结果处理模式，不自动切到

- 旧 attempt 没有保存 resolved endpoint 或 ticket，无法从历史产物确认请求目标。
- Protenix client 对 `PENDING` 每 60 秒轮询且没有内建 wall-clock timeout；进度时间只在
  `RUNNING` 时增长，使永久 `PENDING` 看起来一直停在 0%。

### 解决办法

- 诊断时显式同时设置 `MMSEQS_SERVICE_HOST_URL=https://api.colabfold.com` 和
  `--msa_server_mode colabfold`，不使用 fallback。
- 用相同服务器、相同序列和串行请求隔离网络、GPU、输入与 endpoint 差异。
- 保留低预算预测只作为工程连通性证据，不把 pLDDT 或单次结构解释为科学成功。
